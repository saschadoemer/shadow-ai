# Architecture — Shadow AI

How the code is cut, what the state looks like, how a frame happens, and how a map gets from
Tiled into the game. The decision behind all of it is ADR-0001: an own minimal engine on
TypeScript and Canvas 2D, no framework.

## 1. Directory structure

```
src/
  main.ts        bootstrap only: creates the canvas, loads assets, starts the loop, wires input,
                 game and renderer together – the one file that knows both sides
  engine/        generic and game-agnostic: the fixed-step loop, keyboard state, image loading,
                 Tiled JSON → TileMap, camera math, AABB-against-grid collision
  game/          Shadow AI itself: the GameState type and update(state, input) – plain data,
                 pure functions, no DOM, no Canvas, no window (INV-1, INV-2)
  render/        the Renderer interface and its Canvas 2D implementation; scaling and letterbox
  text/          the language table and the TextKey type (INV-4)
public/
  maps/          Tiled maps as JSON, committed as authored – source and runtime file are the same
  tiles/         tilesets as PNG, generated by tools/gen-tiles.ts and committed
tools/
  gen-tiles.ts   the placeholder tile generator (visual.md §5)
tests/
  unit/          Vitest, headless: engine math, game rules, map loading, assets
  arch/          the import and source rules behind INV-2 and INV-4
  e2e/           the one Playwright smoke test
```

What may import what: `main.ts` imports everything. `render/` imports `game/` types and
`engine/`. `game/` imports `engine/` math and `text/` keys, nothing else. `engine/` imports nothing
from the project. `tests/arch/` enforces the two arrows that matter: nothing in `game/` reaches
`render/` or the DOM.

## 2. The state model

One `GameState` object holds everything that changes while playing: the current map id, the
player (position in pixels, facing, animation frame and timer), the camera position, and later
NPCs, captured creatures, cleared regions and the journal. It is plain data: numbers, strings,
booleans, arrays and plain objects. No functions, no class instances, no `Map` or `Set`, no
`Date`. A JSON round trip reproduces it exactly, and a test proves that on a populated state.

Static content — the tile map, tileset properties, sprite definitions, the language table — is
not state. It is loaded once and passed in read-only. The rule of thumb: if it would be saved in a
save state, it is in `GameState`; if it ships with the build, it is content.

`update(state, input, content)` advances the state by exactly one logic step and returns the new
state. Whether it mutates in place or returns a copy is an implementation choice per module;
what it may not do is read anything but its arguments or write anything but its result.

## 3. The loop

Fixed step at 60 Hz (INV-3), rendering once per browser frame:

```
accumulator += min(elapsed, cap)
while accumulator >= step:          step = 1/60 s
    state = update(state, input, content)
    accumulator -= step
render(state, content)
```

The cap limits catch-up after a stall to five steps; anything beyond is dropped, so a background
tab does not fast-forward the game on return. Rendering draws the latest state without
interpolation — with integer pixel positions there is nothing to interpolate. The loop is a pure
function of a clock and is tested with a fake one.

## 4. Input

`engine/input` keeps the current keyboard state: which keys are down this step, which went down
this step. The game reads named actions — `up`, `down`, `left`, `right`, `fullscreen`, later
`lamp` and `journal` — never key codes. The mapping from keys to actions lives in one table in
`main.ts`, so a gamepad (plan M5) and remappable keys are additions to the table, not changes to
the game.

## 5. The renderer interface

`render/renderer.ts` declares what the game needs drawn, in game pixels on a 320x180 surface:
tiles from a tileset, sprites from a sprite sheet, later text from a bitmap font and rectangles
for UI. `render/canvas2d/` implements it with the Canvas 2D API, draws to an offscreen 320x180
canvas, and blits that onto the visible canvas at the largest integer factor that fits
(`visual.md` §2). All positions the renderer receives are integers; the camera offset is rounded
before drawing, never after.

The interface exists so the implementation can change (ADR-0001 names PixiJS as the candidate)
without touching `game/`. It is not an abstraction for its own sake: it has exactly one
implementation until a feature needs another.

## 6. Maps and the Tiled pipeline

Maps are authored in Tiled and saved as JSON (`.tmj`) directly under `public/maps/`; the file
Tiled writes is the file the game loads. Tilesets are external (`.tsj`) under `public/tiles/`
beside their PNG. Nothing is converted at build time.

Fixed layer names (INV-7): `ground` and `detail` are drawn below the player, `above` is drawn
over the player, `objects` is an object layer that holds the spawn point and, later, doors, NPCs
and triggers. Whether a tile is solid is the boolean tile property `solid` in the tileset; the
loader builds the collision grid from it. The loader rejects a map with a layer name outside this
set, a missing spawn point, or a tileset whose tile size is not 16.

`engine/tiled` reads only what the game uses: layer data, tile properties, object positions and
names. It does not try to be a general Tiled importer.

## 7. Assets and the tile generator

`tools/gen-tiles.ts` draws the placeholder tileset from code — flat colours and simple patterns
from Endesga 32 — and writes the PNG and the matching `.tsj` with `solid` properties into
`public/tiles/`. Both are committed, so the game runs without a generation step and the asset
tests (INV-6) check the committed files. The generator is deterministic: running it twice yields
identical files.

When the art pass replaces a tileset by hand (`visual.md` §5), that tileset is removed from the
generator's list and the hand-drawn PNG takes its place under the same name and ids. Nothing in
`src/` changes.

## 8. Text and languages

`text/` holds the language table — one object per language, `de` and `en`, same keys — and
exports `TextKey`, a branded string type that only the table produces. The text renderer accepts a
`TextKey` and the current language, nothing else, so a literal string in the game does not
compile (INV-4). The first stage has no text; the module exists so the first dialogue has a place
to go.

## 9. Tooling

| Concern | Tool |
|---|---|
| Language | TypeScript, `strict`, no `any` |
| Build and dev server | Vite |
| Unit, architecture and asset tests | Vitest |
| Smoke test | Playwright, one spec |
| Lint and format | Biome, one configuration |
| Package manager | npm, `package-lock.json` committed |
| Runtime | the current Node LTS, pinned in `.nvmrc` and `engines` |
| Maps | Tiled |

## 10. Dependency policy

Runtime dependencies: none, until a feature needs one and an ADR says which and why. Development
dependencies are the tools above and nothing that drags a framework in through the back door. A
new dependency is a line in the pull request description that says what it does and why it is
not twenty lines of our own code.
