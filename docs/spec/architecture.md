# Architecture — Shadow AI

How the code is cut, what the state looks like, how a frame happens, and how a map gets from
Tiled into the game. The decision behind all of it is ADR-0001: an own minimal engine on
TypeScript and Canvas 2D, no framework.

## 1. Directory structure

```
src/
  main.ts        bootstrap only: creates the canvas, loads assets, starts the loop, wires input,
                 game and renderer together – the one file that knows both sides; keeps the
                 state it rendered last as window.shadowAi.state, the game's one global
  engine/        generic and game-agnostic: the fixed-step loop, keyboard state, image loading,
                 Tiled JSON → TileMap, camera math, collision of a box against solid boxes
  game/          Shadow AI itself: the GameState type and update(state, input, content) – plain
                 data, pure functions, no DOM, no Canvas, no window (INV-1, INV-2)
  render/        the Renderer interface and its Canvas 2D implementation; scaling and letterbox;
                 the draw order of a frame (draw-scene)
  text/          the language table and the TextKey type (INV-4)
public/
  maps/          Tiled maps as JSON, committed as authored – source and runtime file are the same;
                 the floor, floor.tmj, is generated by tools/gen-floor.ts until the art pass
  sprites/       sprite sheets as PNG, generated by tools/gen-sprites.ts and committed
  tiles/         tilesets as PNG with their .tsj, generated by tools/gen-tiles.ts and committed
tools/
  placeholder-tiles.ts  the placeholder tiles as pure data: pixels and the .tsj (visual.md §5)
  gen-tiles.ts          writes them to public/tiles/; `npm run gen-tiles`
  placeholder-player.ts the placeholder figure as pure data: the pixels of its sprite sheet
  gen-sprites.ts        writes the figure, the lamp, the snippet and the overview sheet to
                        public/sprites/; `npm run gen-sprites`
  placeholder-lamp.ts   the placeholder lamp sheet as pure data: the cone of light, one 48x48
                        frame per facing, drawn from game/lamp
  placeholder-snippet.ts the placeholder snippet sheet as pure data: three 16x16 frames
  placeholder-overview.ts the placeholder overview sheet as pure data: two 8x8 frames,
                        a full and an empty heart
  floor-layout.ts       the floor as pure data: the corridors and rooms, the walls and their
                        openings, the closed doors, the spawn, the creatures' points, the
                        wake point and the furniture (world.md §1)
  gen-floor.ts          writes it to public/maps/; `npm run gen-floor`
tests/
  unit/          Vitest, headless: engine math, game rules, map loading, assets
  arch/          the import and source rules behind INV-2 and INV-4
  e2e/           the one Playwright smoke test
```

What may import what: `main.ts` imports everything. `render/` imports `engine/` and the types and
constants of `game/`. `game/` imports the math, constants and types of `engine/` and the keys of
`text/`, nothing else. `engine/` imports nothing from the project. `tests/arch/` enforces the two
arrows that matter: nothing in `game/` reaches `render/` or the DOM.

`window.shadowAi.state` is the state `main.ts` passed to the last render. It exists in every
build, because the smoke test reads the player's position from it against the dev server and
against the container alike. It is read-only by convention; nothing in the game reads it, and
`game/` does not know it (INV-2).

## 2. The state model

One `GameState` object holds everything that changes while playing. Today that is `tick`, the
logic steps since the start, the player, the camera, the lamp, the creatures, the captured
count, overview and the step of the dark; later the current map id, NPCs, cleared regions and the journal join them. It is plain data: numbers,
strings, booleans, arrays and plain objects. No functions, no class instances, no `Map` or `Set`,
no `Date`. A JSON round trip reproduces it exactly, and a test proves that on a populated state.

The player is `{ x, y, facing, frame, frameTimer, grace, recoil }`. `x` and `y` are the feet position in map
pixels, floating point: at 80 px/s a step moves 1.333 px, and the position is rounded only for
drawing (§5). `facing` is one of `'down'`, `'up'`, `'left'`, `'right'`. `frame` is the phase,
0–4: 0 is standing, 1–4 are the walk cycle. `frameTimer` counts the steps spent in the current
phase; when it reaches 7.5 the phase advances and 7.5 is subtracted, so the timer is always a
multiple of 0.5, which floating point holds exactly. `grace` counts the steps the figure is
still safe from a hit, 0–90; `recoil` is `{ dx, dy, steps }`, the push per step in pixels and
the steps it still lasts, all 0 when there is none (feature 0009). `createInitialState(map)` builds the state
before the first step from the map: `tick` 0, the player at the map's `spawn`, facing down,
phase 0, timer 0, `grace` 0, no push. How the player moves, turns and stays inside the map is specified in feature
0004 (`gameplay.md` §8). The player's collision box is the lowest 8 px of the sprite, 12 px wide,
centred under the feet: `[x − 6, x + 6) × [y − 8, y)`. It is derived from the feet when a step
needs it and never stored. A step moves the box on X, then on Y, and snaps each axis flush to the
solid boxes it would enter (`engine/collision`, features 0005 and 0010); then it clamps the feet
to the map. Intervals are half-open, so touching a box is not overlapping it and a box flush
against a wall slides along it. The solid boxes are the union of the three tile layers (§6);
cells outside the map are open, and the clamp keeps the figure on it. The displacement is below
8 px per call, the smaller side of the figure's box: by less, a box cannot be carried across a
strip. The thinnest box is the 2 px partition (feature 0011); the test is not swept.

`camera` is the view's top-left corner in map pixels, two integers. `followPlayer` (`game/camera`,
feature 0006) centres the 320x180 view on the collision box's centre, (x, y − 4), clamps it to
[0, mapWidth − 320] × [0, mapHeight − 180] and rounds (`engine/camera`, `cameraFor`): clamp
first, then round. It is derived from the player after every step and from the spawn at the
start, and kept in the state so a saved game comes back as it was left.
`createInitialState(map)` lives in `game/update` beside `update`, so that `game/state` holds
types and constants only.

`lamp` is `{ on }` (feature 0007): on in every step whose input holds `lamp`, derived from the
input and kept in the state so the renderer knows what to draw and so later fields — strength
(0010), charge (M6) — join it. While it is on, `stepPlayer` keeps the feet where they are, resets
the walk cycle to standing and turns the facing by the walking rule; no collision or clamp runs.
The cone is `game/lamp`: the apex 12 px above the feet, the facing's unit vector, 48 px long and
half-open, opening with slope 1/2 to each side; `inCone(point, cone)` is the one test the game
makes on it, and `FRAME_APEX` names where the apex sits in a 48x48 frame of the lamp sheet, per
facing.

`creatures` is an array of `{ species, x, y, light, home }` in the order of the map's points
(feature 0008). `home` is the point the creature was made from; it never changes (feature 0009). `x` and `y` are the feet in map pixels, floating point, the bottom centre of a 16x16
sprite; the collision box is the figure's, `[x − 6, x + 6) × [y − 8, y)`; the body point is
(x, y − 8). `light` counts the steps the creature has been lit without a break, 0–59. `captured`
is one whole number per species. `update` steps the player, then each creature against the
stepped player (`game/creature`). A creature is lit when the lamp is on, its body point is in the
cone, and no opaque box lies on the line from the figure's box centre (x, y − 4) to the body
point (`engine/collision`, `sightBlocked`, given `map.opaque`, §6); low furniture lets the light
pass but still stops the walk (feature 0011). Lit, it stands and `light` grows by 1; at 60 it
leaves the array and its species' count grows by 1. Not lit, `light` becomes 0 and it moves
toward the figure's feet when they are closer than 64 px and farther than 8 px — by 2/3 px, or by
what is left to 8 px — through `moveBox`, then its feet are clamped so the sprite stays on the
map. `createInitialState` makes the creatures from `map.points` and rejects a name that is no
species.

`overview` is `{ current, max }`, 5 of 5 at the start (feature 0012); `dark` is 0 while the game runs (feature
0009). The order of a step in `update`: the lamp is on when the input holds it and the figure is
not being pushed; the figure is stepped — `grace` drops by 1, not below 0, and a pushed figure
moves by its push through `moveBox` and the clamp, 3 px per step for 8 steps, without reading
the keys, keeping its facing, standing; the creatures are stepped; then the first free creature,
in array order, within 10 px of the feet of a figure whose `grace` is 0 hits (`game/overview`):
one point less, `grace` 90 and a push straight away from the creature — or, with the last point,
`dark` 1, the figure left as it is. A frozen creature never hits. One step holds at most one hit.
With `dark` above 0 a step is `stepDark` and nothing else: `dark` and `tick` grow by 1, the lamp
is off, the input is not read; in the step `dark` becomes 45 the figure stands on the wake point
facing down, standing, not safe and not pushed, overview is full and every creature still in the
array is at its home with `light` 0, `captured` unchanged, the camera on the figure; in the step
it would become 90 it is 0. The wake point is the map's point named `wake`, the spawn when there
is none; two stop the game at the start (`createInitialState`).

Static content — the tile map, tileset properties, sprite definitions, the language table — is
not state. It is loaded once and passed in read-only. The rule of thumb: if it would be saved in a
save state, it is in `GameState`; if it ships with the build, it is content.

`update(state, input, content)` advances the state by exactly one logic step and returns the new
state. `input` is `GameInput`: the four movement actions and `lamp`, as booleans (§4);
`content` is the loaded map. Whether it mutates in place or returns a copy is an implementation
choice per module; what it may not do is read anything but its arguments or write anything but
its result.

## 3. The loop

Fixed step at 60 Hz (INV-3), rendering once per browser frame:

```
elapsed = snap(elapsed)             within 0.25 ms of ½, 1 or 2 steps: exactly that
accumulator += min(elapsed, cap)    counted in steps, not milliseconds
input = readInput()                 once per frame, before the steps
while accumulator >= step:          step = 1/60 s
    state = update(state, input, content)
    accumulator -= step
render(state, content)
```

The cap limits catch-up after a stall to five steps; anything beyond is dropped, so a background
tab does not fast-forward the game on return. Rendering draws the latest state without
interpolation — with integer pixel positions there is nothing to interpolate. The loop is a pure
function of a clock and is tested with a fake one (`engine/loop`: `advance` is the pure core,
`runLoop` drives it from a frame scheduler).

**Snapping.** On a 60 Hz or 120 Hz display a frame lasts almost exactly one step or half of one.
Without snapping the remainder sits on the threshold, and clock jitter of a tenth of a
millisecond gives none and then two steps in a row — the moving picture stops and jumps. Snapped,
a 60 Hz display advances exactly one step per frame and a 120 Hz display one every second frame;
on 59.94 Hz the game runs 0.1 % slow, which nobody sees. Other rates, such as 144 Hz, are not
snapped and show the uneven cadence that a fixed step without interpolation implies.

**Steps, not milliseconds.** The accumulator counts steps. In milliseconds floating point loses a
step: five capped steps of `1000 / 60` ms, subtracted one by one, leave 16.66666666666666 and run
only four.

**Input once per frame.** `runLoop` takes three callbacks: `readInput`, `update` and `render`.
It calls `readInput` once per frame, before that frame's steps, and hands the result to every
step, so every step of a frame sees the same actions; a frame without a step still reads it. The
loop is the one place that knows where a frame begins. `main.ts` supplies `readInput` (§4) and
closes `update` over the map.

## 4. Input

`engine/input` keeps the current keyboard state: which keys are down, by `KeyboardEvent.code`, so
the physical key counts and the layout does not — W is W on QWERTZ and on QWERTY. On `blur` of
the window and when the document turns hidden (`visibilitychange`), every key is released,
because no `keyup` will come for what is held. A `keydown` with `repeat` changes nothing. That
matters after a release: a key still held when the page regains focus keeps repeating, and must
not press itself again, so the figure stands until the key is really pressed again. The keyboard
does not keep which keys went down this step, the edge a single press needs: nothing in the game
needs one — the lamp is held, not toggled — so the journal (M4) is the first that may.

The game reads named actions — `up`, `down`, `left`, `right` and `lamp`, later `journal` — never
key codes. The mapping from keys to actions lives in one table in `main.ts`: `up` ← ArrowUp or W,
`down` ← ArrowDown or S, `left` ← ArrowLeft or A, `right` ← ArrowRight or D, `lamp` ← Space,
`fullscreen` ← F.
Once per frame, before the steps (§3), `main.ts` resolves the held keys through the table with
`resolveActions`, a pure function in `engine/input`: an action is on when any of its keys is
down. The game gets the five actions as booleans and nothing else. A gamepad (plan M5)
and remappable keys are additions to the table, not changes to the game.

A bound key pressed without Ctrl, Alt or Cmd belongs to the game: `main.ts` prevents its default,
so the arrow keys never scroll the page and Space neither scrolls nor clicks a focused control.
With Ctrl, Alt or Cmd the browser keeps its own shortcut.
`fullscreen` is toggled in `main.ts` on the `keydown` of F without `repeat` and without Ctrl,
Alt or Cmd; it never reaches the game.

## 5. The renderer interface

`render/renderer.ts` declares what the game needs drawn, in game pixels on a 320x180 surface:
tiles from a tileset, sprites from a sprite sheet, rectangles in a palette colour (from feature
0009 on, the lids of the dark), later text from a bitmap font. `render/canvas2d/` implements it with the Canvas 2D API, draws to an offscreen 320x180
canvas, and blits that onto the visible canvas at the largest integer factor that fits, counted
in device pixels (`visual.md` §2). `render/scale` computes that layout as a pure function of the
page area and the device pixel ratio; `main.ts` reads both every frame, so resize, zoom,
fullscreen and a move to another monitor share one path, and the renderer resizes the canvas
only when the layout changes. All positions the renderer receives are integers; the camera
offset is rounded before drawing, never after. `drawLayer` draws cell (c, r) at
(16c − camera.x, 16r − camera.y), and only the columns ⌊camera.x / 16⌋ … ⌊(camera.x + 319) / 16⌋
and the rows ⌊camera.y / 16⌋ … ⌊(camera.y + 179) / 16⌋, cut to the map — at most 21 × 13 cells
per layer; a cell at the view's edge is clipped by the surface. Away from the map's edges the
figure sits at screen (152, 70) for every fractional position, because the camera and the
sprite round the same value.

`drawSprite(sheet, frame, x, y)` draws frame `frame` of a sprite sheet — frames of the sheet's own
`frameWidth × frameHeight` in one row; the figure's are 16x24, the lamp's 48x48 — with its
top-left corner at (x, y), from the decoded image like `drawTile`, smoothing off.
`render/draw-scene` holds the draw order of a frame: clear, then `ground`, `detail`, the lamp's
cone when the lamp is on, the creatures in array order, the player, `above` (§6), the hearts of
overview, the lids of the dark. The player's sprite has its top-left corner at
(round(x) − 8 − camera.x, round(y) − 24 − camera.y): the feet are the bottom centre of the
sprite, so they sit on the tile grid and the figure stands on its tile. Its frame in the sheet is
facing × 5 + phase (§7). The cone's frame is drawn with its top-left corner at the apex,
(round(x), round(y) − 12), minus the frame's apex pixel (`game/lamp`, `FRAME_APEX`: down (24, 0),
up (24, 47), left (47, 24), right (0, 24)), minus the camera; its frame is the facing's index.
Cone and figure round the same values, so they agree pixel for pixel, and the cone lies under the
figure. A creature's frame has its top-left corner at (round(x) − 8 − camera.x, round(y) − 16 −
camera.y); its frame is 2 while `light` is above 0, else ⌊tick / 15⌋ mod 2 (feature 0008).

The hearts of overview (features 0009, 0012) are drawn on the surface, not shifted by the
camera: heart i, for i below `max`, has its top-left corner at (4 + 10i, 4), with frame 0 when i is below
`current`, else frame 1. With `dark` = d above 0 two rectangles in `#181425` are drawn last,
(0, 0, 320, L) and (0, 180 − L, 320, L), with L = min(3 × min(d, 90 − d), 90): they close in 30
steps, stay closed for 30 and open in 30. While `grace` is above 0 the player's sprite is left
out in every frame in which ⌊grace / 4⌋ is odd; the cone is drawn as before.

The interface exists so the implementation can change (ADR-0001 names PixiJS as the candidate)
without touching `game/`. It is not an abstraction for its own sake: it has exactly one
implementation until a feature needs another.

## 6. Maps and the Tiled pipeline

Maps are authored in Tiled and saved as JSON (`.tmj`) directly under `public/maps/`; the file
Tiled writes is the file the game loads. Tilesets are external (`.tsj`) under `public/tiles/`
beside their PNG. Nothing is converted at build time. The floor, `public/maps/floor.tmj`,
108x80 tiles, is generated from `tools/floor-layout.ts` until the art pass (§7) and opens in
Tiled like any other map.

Fixed layer names (INV-7): `ground` and `detail` are drawn below the player, `above` is drawn
over the player, `objects` is an object layer that holds the spawn point and named points —
creatures today, later doors, NPCs and triggers. Whether a tile is solid, and which part of it,
is a property of the tile in the tileset (feature 0010): the boolean tile property `solid` makes
the whole tile solid, the box (0, 0, 16, 16); a tile without it may carry rectangles drawn in
Tiled's tile collision editor, its `objectgroup` in the `.tsj`, each a box in tile-local pixels.
A wall thinner than a tile is such a rectangle. The loader builds the solid boxes from both.
The boolean tile property `low` (feature 0011) marks a tile whose boxes stop feet but not light,
like a desk or a partition; a tile that is `low` and has no box is rejected.
**Loading.** `main.ts` loads the map, its tileset and the tileset's image before the first frame;
until then the page shows its background. Every path inside a file is resolved against that file
— the map names `../tiles/placeholder.tsj`, the tileset names `placeholder.png` — and all three
come from the game's own origin (INV-5). `engine/assets` does the fetching; `resolvePath` uses a
`file:///` base, because the build may contain no `http://` URL. The map is content, not state
(§2).

**Parsing.** `engine/tiled` holds three pure functions over parsed JSON. `tilesetSource` finds
the map's one external tileset; `parseTileset` reads its tile size, columns, tile count, image
and per tile its boxes — the full tile for `solid`, else its collision rectangles, else none —
as `Tileset.boxes`, and per tile whether it is `low` as `Tileset.low`; `parseTileMap` reads the map against the parsed tileset and
returns a `TileMap`. It reads only what the game uses: of the map `orientation`, `infinite`,
`width`, `height`, `tilewidth`, `tileheight`, `tilesets` and `layers`; of a layer `name`, `type`,
`data`, `encoding`, `compression` and, for `objects`, the objects' `name`, `point`, `x` and `y`.
`TileMap.points` are the point objects other than the spawn, as `{ name, x, y }` in file
order; `engine/` does not know what a name means, `game/` does. The game knows the species'
names and `wake` (feature 0009). Everything else Tiled writes is
ignored — a layer hidden in Tiled is drawn by the game. It does
not try to be a general Tiled importer.

**The TileMap.** Width and height in tiles; `ground`, `detail` and `above` as row-major arrays
of tileset ids, where gid 0 becomes `EMPTY` (−1) and gid `g` becomes `g − firstgid`; an absent
`detail` or `above` is all `EMPTY`. The `spawn` point is in pixels, and so are the named
`points`. `solids` is row-major, width × height: per cell the boxes of its tiles on the three
layers, moved to map pixels, so collision has one list per cell to ask; a cell with no box is
open. A box is half-open: (x, y, width, height) covers [x, x + width) × [y, y + height).
`opaque` is built the same way from the tiles that are not low; a cell with no such box shares
the empty array. `moveBox` reads `solids`, for the figure and the creatures alike; `isLit` hands
`sightBlocked` a grid whose boxes are `opaque`, so the light stops at walls, closed doors and
cabinets and passes over everything lower than a person (feature 0011).

**What the loader accepts.** An orthogonal, finite map with 16x16 tiles, at least 20x12 tiles
(320x180 px, the surface); exactly one external `.tsj` tileset with 16x16 tiles; layer data in
Tiled's default CSV, an array of whole numbers of length `width × height`; the layers `ground`
and `objects`, and optionally `detail` and `above`, each at most once; a spawn inside the map and
outside every solid box; every named point inside the map and outside every solid box. A point
in the open part of a wall cell is accepted.

**What it rejects.** Anything else stops the game before it starts, with an error that names the
file and the problem. First the tileset: not exactly one tileset in the map, an embedded tileset,
a source that does not end in `.tsj`, a `.tsj` that does not load, a tileset whose tiles are not
16x16, a tileset tile with an `animation`, and per tile, in this order: a collision object that
is not a rectangle (an ellipse, a point, a polygon, a polyline, a text or a tile object), a
rotated one, a rectangle that is not whole pixels inside the tile — a fractional number, a width
or height below 1, any part outside [0, 16) × [0, 16) — and a tile that is `solid` and has
collision rectangles, and a tile that is `low` and has no collision box (`tile N is low but
has no collision box`). Then the map, in this order:

- an orientation other than orthogonal, or an infinite map;
- a tile size other than 16x16;
- a map under 20x12 tiles;
- per layer, in file order: a name outside the four, a type that does not match the name
  (`objects` an object layer, the others tile layers), a name used twice, an `encoding` other than
  CSV or any `compression`, a cell count other than `width × height`, a cell that is not a whole
  number, a gid with one of Tiled's four flip or rotation bits set, a gid outside the tileset;
- a missing `ground` or `objects` layer;
- no point object named `spawn` in `objects`, or more than one;
- a spawn outside the map, or inside a solid box of its cell;
- a point object without a name;
- a named point outside the map, or inside a solid box of its cell.

Last, the tileset's image must load.

Flipped and rotated tiles, more than one tileset per map, embedded tilesets, encoded or
compressed data and infinite maps stay rejected until a feature needs one and lifts its rule. A
tileset tile with an `animation` is rejected too: the game has no animated tiles, and a still
image in place of one would be a silent lie.

## 7. Assets and the generators

`tools/placeholder-tiles.ts` draws the placeholder tileset from code — flat colours and simple
two-colour patterns from Endesga 32 — and returns the pixels and the matching `.tsj` as data.
`tools/gen-tiles.ts`, run with `npm run gen-tiles`, writes them as `public/tiles/placeholder.png`
and `public/tiles/placeholder.tsj`. Node runs both files directly, without a transpiler; that is
why `tsconfig.json` allows `.ts` extensions in imports. Both files are committed, so the game runs
without a generation step and the asset tests (INV-6) check the committed files. The generator is
deterministic: running it twice yields identical files, and a unit test fails when the committed
files and the generator disagree.

An interior wall is a strip 4 px thick on the **top** or the **left** edge of a cell, so the
cell's floor belongs to the room below or right of it and a room loses no cell to its walls. A
wall tile is its floor tile with the strip drawn over it, because `ground` holds one tile per cell
and `detail` stays free for furniture; the corridor wall tiles are the carpet ones plus 4. A
strip's pixels are exactly its box: `#262b44` with its inner line, the row y = 3 or the column
x = 3, in `#3a4466`, the corner square dark; the door strip `#733e39` with its row y = 3 in
`#3e2731`. Pixel (0, 0) of the two floor tiles is their base colour. The furniture tiles 13–29
(feature 0011) are transparent where nothing is drawn; their colours and pixels are those of the
feature spec's tile table, and none uses `#68386c`. A partition's pixels are exactly its boxes.
The `.tsj` has `columns` 15, `tilecount` 30, `image` `placeholder.png`, a `solid` property of type
`bool` on tiles 2, 3, 16–19, 21 and 25–27, a collision `objectgroup` on tiles 4–15, 20, 23, 28
and 29, and a `low` property of type `bool` on every tile but 0–12, 21, 22 and 24. The two tops,
22 and 24, have no entry.

Every `.tsj` under `public/tiles/` is checked against its PNG: `imagewidth` and `imageheight`
equal the PNG's size, `tilewidth` and `tileheight` are 16, `columns` equals `imagewidth / 16`, and
`tilecount` equals `columns × imageheight / 16`.

When the art pass replaces a tileset by hand (`visual.md` §5), that tileset is removed from the
generator's list and the hand-drawn PNG takes its place under the same name and ids. Nothing in
`src/` changes.

`tools/placeholder-player.ts` draws the placeholder figure the same way, from code in six
Endesga 32 colours, and returns the pixels of its sprite sheet as data; it is pure.
`tools/gen-sprites.ts`, run with `npm run gen-sprites`, writes them as `public/sprites/player.png`.
The sheet is 320x24: twenty 16x24 frames in one row. Frame index = facing × 5 + phase, facings in
the order down (0–4), up (5–9), left (10–14), right (15–19); phase 0 is standing, phases 1–4 are
the walk cycle in order. Facing right is facing left mirrored.

The sheet is not a tileset: it lives under `public/sprites/`, has no `.tsj`, and the
multiple-of-16 rule applies to `public/tiles/` only. The palette, alpha and reserved-colour rules
apply to it as to every PNG under `public/` (INV-6). Like the tiles, the sheet is committed and
its generator is deterministic; a unit test fails when the committed PNG and the generator
disagree. When the art pass draws the figure by hand (`visual.md` §5), the hand-drawn PNG
replaces `public/sprites/player.png` under the same name and frame order. Nothing in `src/`
changes.

`tools/placeholder-lamp.ts` draws the lamp sheet the same way and returns its pixels as data:
`public/sprites/lamp.png`, 192x48, four 48x48 frames in one row in facing order down, up, left,
right, each a checkerboard of `#fee761` cut to the cone from the frame's apex pixel, drawn from
`inCone` of `game/lamp` so the picture is the rule. `npm run gen-sprites` writes both sheets; both
are committed, the generator is deterministic, and a unit test fails when the committed file and
the generator disagree — for the lamp it re-derives every pixel from `inCone` and counts 576
opaque pixels per frame. When the art pass draws the cone by hand (`visual.md` §5), the
hand-drawn PNG replaces the file under the same name, frame order and apex pixels, and the
generator and its tests go; the frame size and the apex pixels stay, because the renderer places
the frame by them.

`tools/placeholder-snippet.ts` draws the snippet sheet (feature 0008) and returns its pixels as
data: `public/sprites/snippet.png`, 48x16, three 16x16 frames in one row — the scrap, the scrap
2 px higher, the scrap with white paper. Border and lines of text are `#68386c`, the paper
`#c0cbdc`, the lit paper `#ffffff`; 100 opaque pixels per frame, 52 of them the signature colour.
`npm run gen-sprites` writes it beside the other two; it is committed, deterministic and tested
against the generator. The art pass replaces it under the same name and frame order.

`tools/placeholder-overview.ts` draws the overview sheet (features 0009, 0012) and returns its
pixels as data: `public/sprites/overview.png`, 16x8, two 8x8 frames in one row — a heart 7 wide
and 7 high, 34 opaque pixels, with a rim of 16 in `#181425`, inside 18 in `#e43b44` for the full
heart and `#3a4466` for the empty one. `npm run gen-sprites` writes it beside the other three; it is committed,
deterministic and tested against the generator pixel by pixel. The art pass replaces it under the
same name and frame order.

`tools/floor-layout.ts` holds the floor as data (feature 0010) — the corridors and rooms as
rectangles of floor, the walls as lines of top or left strips with their openings, the closed
doors, the spawn, the three snippet points and the wake point, as the tables of the feature spec
write them — and builds the `ground` layer and the `.tmj` object with Tiled's keys. The furniture
(feature 0011) is `FURNITURE`, the room table as a list of placements per area — workplaces,
cubicles in banks, islands, café tables, screens, tables, counters, chairs, printers, plants and
cabinets — and `buildFurniture` turns it into the `detail` layer and, for the tops of cabinets and
plants, the `above` layer; a second tile in a cell of one layer is an error, not an overwrite.
`floor.tmj` has the layers `ground` (id 1), `detail` (id 3), `above` (id 4) and `objects` (id 2),
in that order. Posts are
derived, not listed: a cell with no strip whose left neighbour has a top strip and whose upper
neighbour has a left strip gets the post tile. `tools/gen-floor.ts`, run with `npm run gen-floor`,
writes `public/maps/floor.tmj`, deterministic, with the layer's data on one line as Tiled writes
it. A unit test fails when the committed file and the generator disagree, and proves the layout
against the spec's tables: the ring and its windows, every interior cell in exactly one area,
every wall cell with its strip and every opening without, the posts, the closed doors, the tile
counts, a free spawn and its first view, reachability on foot over a 2 px lattice of feet
positions — every corridor and room but the lift and the stairwell, the meeting rooms only
through the side passage — and for each snippet and the wake point a free box, a reached position
and its place; and the furniture against the spec's picture, its tile counts, its pieces, the
areas that stay empty, every tall thing's top above its body in the same area, every cubicle
reached, the reception's counter in the first view, and which boxes are opaque. The file's whitespace is not Tiled's; a save in Tiled reformats it and fails that
test, so until the art pass the layout changes in `floor-layout.ts`. When the art pass takes the
floor over by hand (`visual.md` §5), the layout, the generator and the determinism test are
removed and `floor.tmj` is authored in Tiled like every other map; the layout test's
reachability and closure checks stay.

## 8. Text and languages

`text/` holds the language table — one object per language, `de` and `en`, same keys — and
exports `TextKey`, a branded string type that only the table produces. The text renderer accepts a
`TextKey` and the current language, nothing else, so a literal string in the game does not
compile (INV-4). The first stage has no text; the module exists so the first dialogue has a place
to go.

## 9. Tooling

| Concern | Tool |

| Language | TypeScript, `strict`, no `any` |

## 10. Dependency policy

Runtime dependencies: none, until a feature needs one and an ADR says which and why. Development
dependencies are the tools above and nothing that drags a framework in through the back door. A
new dependency is a line in the pull request description that says what it does and why it is
not twenty lines of our own code.
